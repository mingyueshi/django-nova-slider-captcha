## 变更从哪一次请求生效

主控用同一进程、同一启用 CSRF 的 Django 测试客户端预热配置，签发多道 `demo` 挑战，并分别保留待验证的挑战、已签发尚未消费的凭证和已经验证成功的表单。每次验证使用测试进程预设的题位。下表在旧版、候选源码和安装本次 wheel 的环境中分别核对。

| 设置操作 | 下一次调用的实测结果 |
| --- | --- |
| 通过 `override_settings()` 替换白名单和策略，或直接对 settings 赋值，或对原列表及策略字典原地修改 | 三种方式删除 `demo` 后，旧挑战得到 `invalid_challenge`，没有生成凭证或增加尝试次数。旧凭证在演示提交端返回 403，直接调用消费服务返回 `False`，数据库消费标记保持为假。为该用途发新题返回 400，保留的 `login` 用途仍可验证。 |
| 用删除前的凭证新建表单，再次校验一个删除前已经成功的表单 | 两个表单都拒绝放行。已经观察到配置变化的旧表单实例，在用途恢复后仍保持失效。 |
| 原地清空白名单，或删除用途但遗留对应策略项 | 系统检查分别得到 `E004` 或 `E006`，已初始化会话的验证接口返回 503。修正配置后的下一次调用即恢复。 |
| 原地把用途策略从 61 秒、2 次、容差 1 改为 92 秒、6 次、容差 5 | 新发题按 92 秒写入过期时间。相同的位置偏差在旧题被拒绝并剩 1 次，在新题通过。旧题到期时间及原策略快照保留。 |
| 嵌套覆盖全局 TTL，再逐层退出 | 新发 `login` 题的 TTL 依次为 35、73、35、120 秒。另验证直接删除设置后使用默认值，将等值整数换为布尔值或浮点数仍按非法配置处理。 |
| 预热已有的 GCRA 限流桶后原地调整容量 | 在同一时刻把容量从 10 降至 1 后，下一次请求被拒绝。调回 10 后恢复放行，已有桶债务继续参与判断。 |

删除用途的约束适用于该用途被禁用期间。沿用基线行为，宿主若显式重新启用同名用途，尚在有效期内的旧挑战和未消费凭证可以重新使用。主控确认该凭证恢复后首次消费成功，重放返回 403。

## 缓存与并发

每次读取配置时，全局策略按当前 TTL、次数、容差取值，小型用途白名单按当前内容取值。两处进程内 LRU 各保留至多 16 项，只复用校验成功的结果。超过 64 项的合法白名单继续可用，逐用途策略表在每次读取时整体校验，所以嵌套字典的原地改动也立即生效。

在 80 次不同配置之间切换后，两处缓存均保持在 16 项以内。70 项白名单仍能读取，150 个未知请求用途均被拒绝。仓库回归还确认小白名单在接收不同请求用途时，缓存命中增加而条目数和未命中次数保持不变。

主控在一个线程的旧白名单校验中设置屏障，在另一线程替换白名单并成功读取新配置，再放行旧线程。此后六次跨线程读取均只允许新用途。实施回归也覆盖了旧全局策略较晚完成的情况。生效点是当前进程的下一次配置读取，已开始的调用可能持有此前的值。部署时各 worker 仍须分别加载同一份新配置。

主控在 Python 3.12.16 中用同一组 Django 设置交替测量基线和候选版本，预热后取 9 轮中位数。每轮按发题路径重复一组 7 次配置读取，包含两次策略读取、一次读取白名单、两次限流读取、两次用途校验。后两组配置为每个用途设置 TTL 与次数覆盖，并设置 IP 与会话限额。
