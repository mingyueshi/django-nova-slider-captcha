## 事务提交与回滚

使用启用 CSRF 的 Django 测试客户端走发题、验证和受保护的演示提交接口。把验证码写入单独的 `captcha` 数据库，测试接收端仅监听本机回环地址，通过独立 TLS 连接收取通知。接收端在收到 POST 时用另一个 SQLite 连接读取预设测试题的状态。

| 场景 | 独立实测结果 |
| --- | --- |
| 默认设置、发题、错误位置、重复验证或消费 | 默认设置下走完验证和消费，收到 0 条通知。启用后，仅首次成功的两次状态变化各产生 1 条，失败及重放均未增加通知。 |
| 嵌套写事务，默认数据库另有未结束的事务 | 离开写库内层保存点时没有通知。写库外层提交后立即可接收，即使默认库事务仍未结束。验证通知到达时独立连接读到“已验证、未消费”，消费通知到达时读到“已验证、已消费”。 |
| 外层回滚、内层保存点回滚 | 在事务中先成功验证并消费，再分别触发两种回滚。接收端均未收到通知，数据库仍是“未验证、未消费”。单独回滚一次消费后，原凭证可成功重试，只发送一次消费通知。 |
| 多字段表单 | 第一个凭证合法、第二个凭证无效时，整表校验失败，第一项消费随事务回滚。接收端没有收到消费通知，第一张凭证仍可使用。 |
| 手动事务与配置变更 | 手动关闭 autocommit，在写库 `atomic()` 内完成验证。回滚无通知，提交并恢复 autocommit 后才收到通知。另在提交前关闭 Webhook，先前登记的通知被丢弃，已提交的凭证仍可消费。 |

## 接收端故障与投递容量

- 让本地接收端持续扣住响应。验证、消费和排在其后的 Django 提交钩子均在接收端放行前完成。再让两次后台投递等待至套接字超时，后台容量正常释放，两次数据库更新均已提交。
- 接收端分别返回 HTTP 503 和 307，另测试连接拒绝、证书不受信任和非法配置。验证与消费均成功。503 只收到原始投递，307 指向的第二路径收到 0 个请求。非法配置得到 `nova_slider_captcha.E011`。仓库回归另覆盖后台线程无法启动时的容量释放。
- 占满四个后台投递槽位后，下一次验证与消费仍成功，两条通知被丢弃。释放槽位后新通知恢复发送。另在独立进程占满父进程的四个槽位后执行 fork，子进程获得四个独立槽位。

这是尽力投递。满载或进程退出可能丢通知，两种通知可能乱序，没有持久化补发。Admin 会在校验密码前消费凭证，接收方应使用宿主的业务事件确认登录结果。

主控使用临时测试 CA 和本机 HTTPS 接收端，在候选源码与安装包上分别实收 **22 条 POST**。逐条核对以下内容。

- 正文只有 `event` 与 `notification_id`。事件只取 `verification_succeeded` 或 `proof_consumed`，通知 ID 均为独立 UUID4。固定在同一秒签发两条同类事件，二者 ID 和已签名正文均不同。
- 接收端以独立测试密钥，对时间戳头的 ASCII 字节、点号和实际收到的原始正文重算 HMAC-SHA256，所有签名均匹配。在正文末尾增加一个空格后原签名即不匹配。
- 请求头仅有传输所需的 Host、正文长度、类型、编码协商、Webhook 时间戳与签名。对照客户端和数据库的测试值，未发现凭证、凭证哈希、挑战 ID、会话绑定及其哈希、Cookie、CSRF 值、认证头、客户端 IP 或密钥。正文没有用途、坐标、图片或请求数据。故障检查也未在组件日志中发现测试秘密或响应体标记。
